# Verified accounts: which platforms, and at what cost (issue #58)

Checked: November 7, 2026. Scope: spec sections 8 and 13.3, and Decision 1 in `docs/research/decisions-phase2-v1.md`.

## Owner decision

Issue #58, verbatim: "all services that don't require me to pay a subscription for a low use api access key."

Rule applied here: a platform is included when the pages I read describe no paid plan, subscription, or purchased credit for the API calls a verification needs. App review does not exclude a platform. A platform that needs review is built behind a per-platform flag that defaults off. "No fee stated" means the pages I opened did not mention a price. It is not a promise from the platform that the API is free. A platform is excluded when its published terms require paid credits, or when it cannot prove control of the claimed account.

## What was built

- **Platforms in the claims UI:** GitHub, Mastodon, Website, Domain, Bluesky, Instagram, Threads, TikTok, YouTube, Twitch, and X (page check only, see below). Platforms that sign in through a provider app show "(not available yet)" until their flag is on. The "coming later" entries are gone.
- **Flags:** a provider turns on only when `VERIFY_<PLATFORM>_ENABLED` is exactly `true` and both credentials are set. Names are in `.env.example` and `docs/deploy.md`.
- **Callbacks:** all providers share `/account/claims/callback`. A state row (single use, 15 minutes) names the provider and the claim. The callback checks that the account the provider reports is the claimed account, writes the attestation, and discards the token. Secrets come from the environment only.
- **Claim addresses:** TikTok `https://www.tiktok.com/@name`, Threads `https://www.threads.com/@name`, Twitch `https://www.twitch.tv/name`, YouTube `https://www.youtube.com/channel/UC...` (the channel ID, because an `@handle` cannot be matched without a lookup), Bluesky `https://bsky.app/profile/<handle or DID>`, Domain `https://<host>`.
- **Proof text:** `blueyvatar-verify=<DID>`. It names the DID, so a proof placed for one account does not verify another. Only someone who controls the bio or the DNS zone can place it.
- **Re-check job (spec section 8 timing unchanged):** domain and Bluesky claims re-run the same proof check. Provider claims cannot re-run the sign-in because the token is not kept, so the job fetches the account page and fails the claim only on 404 or 410. Every other answer is inconclusive and never counts as a failure. Three consecutive failures revoke the badge, as for the existing methods.
- **Profile page:** each verified account shows its platform name and a check mark.
- **Migration:** `db/migrations/0018_verified_accounts_providers.sql` (0016 and 0017 were already taken on main).

## Limits and open items

- No provider could be called live: there are no credentials in this environment. The provider code follows the response shapes on the pages cited and is tested against stubbed responses. Two shapes I could not confirm from the pages: the nested `data.user.username` layout of the TikTok user info response, and whether Twitch accepts an empty `scope` and returns `login` from Get Users without one. Check both with the first real sign-in, before the flag is switched on for users.
- The Instagram username page documents `/me` with a `data` array; the code accepts either that layout or fields at the top level.
- X claims keep the existing rel="me" page check. It reads the public page and does not call the X API, so it costs nothing, and the claims page already warns that X may hide bio links from crawlers.
- A domain claim proves control of the DNS zone for that exact host. It does not prove control of a website on it.
